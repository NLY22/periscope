# 项目分析与扩源主链审计

日期：2026-10-22。

后续跟踪：2026-10-24 已修正新入库评论丢失、正文回填覆盖元数据与分层问题，并优化浏览器等待、部分结果保存和超时清理。范围、验证方式及仍未完成的对象更新／多轮整合见[当前采集链路](collection-pipeline.md)。下文保留原审计日期的发现与复现记录。

本次检查代码、测试和设计记录，并使用隔离样本验证采集、入库、正文合并与查询预算。没有修改产品代码，也没有重新执行真实平台采集、付费搜索对照或平台登录。

## 1. 结论

项目已有可复用的多源采集、网页／文本 PDF 提取、资料入库、全文检索和旧研究能力。当前主要形态是新版单轮检索与旧版研究产品并存。

已确定的目标是取得通用搜索覆盖不足的有效资料，并通过用户主导的多轮调查逐步缩小信息缺口。当前还不能将项目称为已经完成的深层讨论采集与多轮调查系统：12 个目标平台的完整能力未逐项验收，新调查控制器与结构化资料版本仍停留在设计阶段。

优先事项应是修通原始资料的保存与回读，按批次验证实际扩源价值，再将稳定的采集动作接入统一调查流程。

## 2. 当前结构与已有能力

| 部分 | 当前实现 | 判断 |

## 3. 已复现的正确性问题

### P1：正文缓存合并覆盖来源信息并破坏内容分层

位置：[正文缓存合并](../periscope/operations/ingest.py#L438)，关键更新位于该文件第 483 行；全量入库路径第 771 行存在相同更新形式。

合并时将 `metadata_json` 整体替换成仅含 `fulltext` 的对象，同时将新正文直接写入 `claimable`，却没有同步维护 `sections_json`。

隔离复现结果：

- 合并前元数据包含 `source_key`、`source_kind`、`provenance` 和 `metrics`；合并后只剩 `fulltext`。
- 样本原本被标记为社区内容，可供声明取证的文本长度为 0；合并后变为 880 字符。
- 正文已替换，但原有分层正文仍然保持旧内容。

影响：来源追溯信息丢失，内容、分层与取证索引不一致；社区材料可能进入作者正文取证通路。应统一修正两条合并路径，保留原元数据，并依据实际资料角色同步更新分层及相关派生数据。

### P1：新版查询记录中的评论未进入可检索资料

位置：[查询记录字段](../periscope/topics/runs.py#L39)、[采集行转资料条目](../periscope/operations/ingest.py#L298)。

运行记录会保留 `comments`，但 `build()` 转换 HTTP 型采集行时只选择正文及部分元数据，没有转换评论正文或其关系。

隔离复现中，一条查询 JSON 带有 1 条评论；调用实际转换函数后，生成的资料对象全文与元数据中均没有该评论文本。

影响：查询记录能看到评论，后续通过语料库检索和追问却找不到这部分材料。该结论针对新版查询 JSON 到入库的路径；不表示旧抓取器写入正文内的所有评论都被丢弃。应将评论、回答与回复保存为有稳定编号及关系的资料，保留独立作者与来源角色。

### P2：普通条目的再次采集无法补充同一对象的新正文

位置：[普通对象身份](../periscope/operations/ingest.py#L293)、[条目写入](../src/corpus/store.py#L366)。

普通对象按来源和链接生成稳定编号，`Corpus.add_items()` 使用 `INSERT OR IGNORE` 跳过已有编号。隔离样本中同一链接第二次返回变化后的正文，新增条数为 0，数据库仍保存第一次正文。

这是现有追加去重语义与目标更新能力之间的缺口。网页爬虫的文档哈希身份有单独处理，不能推广为所有平台已经支持版本更新。后续需区分对象身份、文本版本和每次观察，保留旧引用并追加变化。

## 4. 与目标有关的主要能力缺口

### 4.1 原文保真仍需贯穿全链

部分 HTTP 解析路径在返回前截取到 1,200 字符，B站评论富化只读取第一页并截取每条 300 字符。历史结果中多数平台仍主要是搜索卡片或描述。

本地检索也有 4,000 字符的回读上限，这是已有的输出大小控制。后续需要区分完整存储与展示／模型片段，提供按需读取原文及明确的截断信息。不能将文本长度达到某个阈值直接解释为已取得完整正文。

位置：[HTTP 文本解析](../periscope/collection/transport/parsing.py#L328)、[B站评论](../periscope/collection/platforms/bilibili.py#L205)、[本地正文回读](../periscope/search/local.py#L370)。

### 4.2 当前预算分阶段，尚未成为统一调查截止时间

当前单轮依次执行 API、直采、可选爬虫及富化。平台直采内部已有预算控制，但 API 没有领取同一个剩余预算，爬虫使用独立 `crawl_budget`，富化也在其后执行。

隔离替身依次收到 API、平台和爬虫调用；平台和爬虫各领取独立 0.025 秒预算，实际总耗时约 0.062 秒。此样本验证的是预算传递方式，不是线上速度。

CLI 已明确把 `--budget` 描述为直采预算、`--crawl-budget` 描述为爬虫独立预算，因此这不是 CLI 参数失效；它表明新调查的“单轮 1–3 分钟”还需在应用控制器中增加共享截止时间。来源限制也要明确区分旧直采筛选语义与新调查全轮限制。

位置：[单轮编排](../periscope/topics/service.py#L31)、[CLI 参数](../periscope/cli/topic.py#L49)。

### 4.3 多轮调查尚未接通新版采集

旧 Web/MCP 调用旧研究编排，新版 `TopicService` 是同步单次查询。设计中的信息缺口记录、轮次取消、逐批资料事件、跨轮固定版本引用和浏览器会话统一管理还需要实现。

实现时保留既有机制，但应围绕新的采集动作和资料契约接通。避免直接将整个旧报告编排导入新版模块，也避免再建立第二套彼此独立的任务所有者。

### 4.4 API 优势对照仍缺内容级证据

当前 `compare_sources()` 统计本轮规范链接差集及带正文结果数，不能识别同一链接下多取得的评论、回复上下文或不同版本，也不能单独证明新增资料相关或改善回答。

需要同时验证“从自然语言问题发现资料”和“针对已知链接深入读取”。对照保留合理查询词、内容获取设置、日期／来源条件、耗时及成本，按相关新增内容计量，并区分公开内容漏检与用户授权带来的访问差异。

位置：[现有覆盖统计](../periscope/topics/coverage.py#L5)。历史 API 探测及其限制见[信息源体系](source-system.md)。本次未据此重新判断某家搜索 API 的实时能力。

### 4.5 低维护目标需要实际验收

当前具备部分持久化浏览器与 Cookie 接入基础，但首批 12 平台的登录复用、失效提示、跳过处理、评论分页和更新能力尚无完整的逐项实测矩阵。应记录成功率、人工处理频率及采集深度，避免将一次请求成功视为可长期使用。

### 4.6 版本交付尚未固化

当前工作区存在大量既有改动，正式的 `periscope/` 实现及多份测试和设计文件仍为未跟踪状态。本次没有暂存、提交或调整这些文件。后续应按可验证批次整理版本记录，保障安装和复现不依赖工作区中未纳入版本的文件。

## 6. 建议推进顺序

1. 先修正正文合并、评论保存及原文／截断信息，保证已取得的内容能完整保存并再次检索。
2. 建立 12 平台的实际能力矩阵，按批次完成自然语言发现、详情、评论分页、回复关系及补新；保留完整目标范围。
3. 每批同步进行内容级 API 对照，记录新增有效资料、来源与重复获取结果，把扩源价值验证前置。
4. 在稳定动作接口和资料关系之上实现最小多轮流程：追问定位对象、针对缺口补采、新指令停止、历史版本引用。
5. 将网页与 MCP 接到同一任务服务，完善按需登录与低维护体验，再做完整界面打磨。

已有[框架设计](superpowers/specs/2026-10-19-local-investigation-source-framework-design.md)仍可作为目标结构参考，但第 13 节将真实对照安排在后段的顺序，建议按本次分析前移。此建议不表示已经实施这些调整。
