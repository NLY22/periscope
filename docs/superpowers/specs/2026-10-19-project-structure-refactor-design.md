# Periscope 项目结构重构方案

日期：2026-10-19  
状态：用户指示先整理现有代码后，已按渐进迁移方案实施；当前结构见 `docs/code-organization.md`。

## 1. 目标与范围

用户要求先重构项目。结合已完成的代码、数据和测试分析，本次目标是让现有项目的职责、依赖、入口和交付方式清晰一致，为后续研究产品开发打好基础。

“漂亮”的验收含义是：能从目录看懂职责；功能实现只有一个归属；命令入口简洁；源码运行与安装运行都可用；现有命令、数据和功能保持兼容。

本次只重构当前话题检索及其采集、保存链路，并修正与之直接相关的打包、容器和说明。旧日报、研究、Web、MCP 保留原实现，继续工作。它们不会在本轮被全部重写。

## 2. 现状与约束

- 新版主链路散布在根目录 `topic.py`、`core/`、`collectors/`、`tools/`。
- `topic.py` 同时负责参数、三层检索、富化、渲染、运行记录和入库子进程。
- `collectors/collector.py` 同时包含源定义、179 个源的目录、解析、请求与分页、认证及批量命令。
- 运行和运维依赖仓库位置、脚本相对路径及多处 `sys.path` 修改。
- 安装包只包含 `src`，Docker 也主要打包旧版产品；新版尚未成为完整交付物。
- 工作区已有大量未提交改动和未跟踪文件；以当前工作区为基线，保留这些工作。
- 新版和旧版默认分别使用两个语料库。数据库位置保持原状，不自动搬移或合并。
- 既有全量测试在前一轮检查中退出码为 0。实施前重新记录基线，完成后再次全量验证。

## 3. 方案比较

| 方案 | 收益 | 代价 | 结论 |
|---|---|---|---|
| 只整理注释和文件名 | 变更少 | 不解决脚本耦合、交付缺失和入口过重 | 不选 |
| 分层迁移，保留兼容入口 | 实现归属明确，可以逐步验证，现有使用方式可继续工作 | 迁移期保留少量兼容文件 | 推荐 |
| 一次性重写新旧全部系统 | 最终目录可以更统一 | 改动范围过大，容易混入功能变化，难以核对现有工作 | 不选 |

## 4. 目标目录与职责

```text
periscope/
├── __init__.py
├── cli/
│   └── topic.py             # 参数解析、调用服务、输出与退出码
├── runtime/
│   ├── paths.py             # 数据、缓存、凭据与浏览器路径
│   └── console.py           # 终端编码和输出
├── topics/
│   ├── models.py            # 查询请求、结果及执行统计
│   ├── service.py           # 三层检索、合并与可选富化的编排
│   ├── render.py            # 当前文本和 JSON 呈现
│   ├── runs.py              # 原始运行分片、查找与重放
│   ├── enrichment.py        # 结果富化与补丁回传
│   └── persistence.py       # 分片转换、入库调用及结果
├── search/
│   ├── local.py             # 本地检索与正文补全
│   ├── api.py               # 现有搜索 API、限流及多问法
│   └── merge.py             # 现有聚合、排序和去重策略
├── collection/
│   ├── sources.py          # Source 模型、目录索引与查询
│   ├── catalog/            # 按类别组织的源定义，保留目录顺序
│   ├── parsing.py          # JSON、RSS、HTML 与字段清洗
│   ├── http.py             # 请求、分页、限流与抓取统计
│   ├── fanout.py           # 多源并发和时间预算
│   ├── credibility.py      # 现有来源先验的适配
│   └── platforms/          # 浏览器与 B 站等平台专属实现
└── operations/
    ├── ingest.py           # 现有分片到语料库的导入
    └── backfill.py         # 现有正文回填

src/                        # 既有证据内核及旧产品，维持兼容
topic.py                    # 旧命令兼容入口
core/                       # 旧导入路径的兼容层
collectors/                 # 旧导入及直接运行脚本的兼容层
tools/                      # 运维入口；已迁移的实现改为薄入口
probes/                     # 已有实验归档，排除在产品安装包之外
tests/                      # 原有测试及必要的迁移契约测试
docs/                       # 当前使用说明、架构与历史记录
```

目录是职责约定，不要求创建没有实际内容的空模块。源目录按照现有类别分组，每个源只定义一次；使用显式汇总顺序，不在导入时动态发现文件。

## 5. 依赖与运行方式

- `cli` 调用 `topics.service`，不承担检索或抓取实现。
- `topics.service` 组合本地、API、平台能力，返回数据；渲染、保存和退出码由各自边界处理。
- `search.merge` 保留为纯数据处理，不依赖 CLI、浏览器或数据库连接。
- `collection` 管理采集行为，源定义与解析代码可以独立导入，不触发采集、浏览器启动或凭据读取。
- 新版允许借用的 `src` 证据内核保持现有白名单。借用集中在确实需要它的本地、入库、正文抽取和可信度适配处，不依赖旧产品的日报、Web、MCP 或研究编排。
- 依赖检查从“旧目录名是否出现”转为检查实际实现所在模块及允许的依赖方向；保留能证明检查有效的反例。
- 应用内部使用包导入和模块入口。仅仓库旧脚本的兼容入口允许为直接运行定位仓库，不再把路径修补散落在业务模块中。
- 保持同步/异步调用边界明确；CLI 负责事件循环入口，异步采集内部不嵌套启动事件循环。

## 6. 兼容性与数据保护

- `python topic.py` 的现有参数、默认档位、文本/JSON 格式和退出语义保留。
- 原有 `core.*`、`collectors.*` 的实际调用接口继续可用。兼容层只转交正式实现，不复制业务代码；既有调用对共享配置和路径的替换应保持一致。
- `tools/topic_persist.py`、`tools/ingest_all.py`、`collectors/backfill_fulltext.py` 等现有脚本继续提供原有功能。
- 原有 `periscope` 日报命令及 Web/MCP 命令保持；新增 `periscope-topic` 作为可安装的话题检索命令。
- `PERISCOPE_DATA_DIR`、`PERISCOPE_SCRATCH_DIR`、`PERISCOPE_COOKIE_DIR` 的现有覆盖语义保留；仓库内默认数据目录保持不变。
- 安装到仓库外时，默认运行数据放在用户可写目录：Windows 使用 `%LOCALAPPDATA%/Periscope`，缺少该变量时使用用户目录下的 `.periscope`；其他平台使用 `$XDG_DATA_HOME/periscope`，未设置时使用 `~/.local/share/periscope`。显式环境变量优先。
- 仓库中的旧凭据文件回退仍可用；安装环境不得向包安装目录写入运行数据，也不得扫描任意目录寻找凭据。
- 不迁移现有大数据库，不删除采集结果，不操作用户浏览器会话，不修改数据库 schema。
- 运行分片现有格式及其重放能力保留，不重新解释旧记录。

## 7. 交付与文档

- 安装包包含新版正式实现及运行所必需的兼容模块；不能依赖源码仓库里的未打包脚本。
- Docker 同时具备运行旧入口和新版话题入口所需的源码；通过显式命令选择入口，保留当前默认行为。
- 安装包和容器上下文排除本机数据库、浏览器配置、凭据、缓存、探测产物和测试临时数据。
- README 先说明当前产品、可用入口和最短使用路径；旧版能力另列，避免把两套链路说成已经贯通。
- 架构说明记录正式模块、兼容层和数据位置；历史重构记录保留为历史材料。
- 注释描述当前行为、约束和理由；清理已失效的路径说明及重复的修复故事。

## 8. 验收

1. 重构前后的原有测试均能执行；新增测试覆盖服务与旧入口的一致性、配置共享和模块导入无采集副作用。
2. 使用固定本地材料和替身 API/采集器，比较新旧入口的结果、排序、运行分片与保存行为。
3. 在临时目录完成“查询 → 保存分片 → 显式入库 → 再查”的验证，不写入现有真实语料库。
4. 构建 wheel，并在隔离目录、脱离仓库工作目录的条件下验证安装后的 CLI 和需要的运维链路。
5. 检查安装包文件清单、Docker 构建输入和入口；环境有可用 Docker 时再验证镜像构建，否则明确记录未运行部分。
6. 执行全量测试和项目现有检索评测；区分环境限制、原有问题与本次引入的问题。
7. 每个业务实现只有一个实际归属；兼容层不保留另一份检索、解析、采集或入库算法。

## 9. 本轮不包含的行为变更

前次诊断确认的引用局部编号错指、合并正文与 URL 来源错配、独立来源口径不统一，继续作为已知问题单独记录。本轮保持排序、合并和研究语义，避免用结构重构掩盖行为变更。

交付验证中另行确认并修正两项与迁移链路直接相关的问题：相对路径跨子进程漂移，以及 `--save` 将运行记录字典直接交给只接受行列表的入库器。两者均增加回归测试；不改变内容排序或研究结论。

也不在本轮新增择校功能、论文搜索产品、研究 UI、自动补证、默认自动入库或数据库合并。

## 10. 执行顺序与下一步

实施将按“建立兼容与运行基础 → 拆分采集目录和引擎 → 拆分话题服务与入口 → 迁入必要运维实现 → 补齐交付和文档 → 整体验证”的顺序逐步进行，每一步保持已有入口可用。

用户审阅本方案后，再编写逐项实施计划。方案审阅只需确认范围与目标，不需要提供具体院校、年份或研究选题。
