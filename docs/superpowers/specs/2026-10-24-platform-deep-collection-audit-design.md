# 首批平台深采能力验收设计

## 意图

项目目标是取得通用搜索容易漏掉的平台原文和讨论。当前搜索入口与深采能力混在描述中，用户无法判断某个平台是否真的支持详情、评论、回复和后续更新。本轮先给 12 个目标平台建立可复查的能力基线。

## 目标与边界

- 平台范围：小红书、知乎、微博、B站、抖音、快手、V2EX、GitHub、Stack Overflow、Hacker News、CSDN、掘金。
- 按搜索发现、正文、评论、楼中楼／回复、分页／覆盖说明、保存后回查六项记录状态；状态区分代码路径、历史产物证据、本轮匿名公开样本，不以配置存在推断支持。
- 用合成或隔离存储验证能取得的资料可入库、回读和保留讨论关系；有网络条件时按现有匿名公开适配器做小规模实时探测，并记录日期、查询、条数、耗时和失败原因。
- 被登录、验证码、限流或地区限制挡住的能力标记为未验证／需授权，不绕过访问控制。
- 不读取个人浏览器配置、Cookie 或密钥，不写入真实语料库，不声称覆盖率或相对搜索 API 的优势。

## 非目标

- 本轮不实现新的平台爬虫、不接通 Web/MCP 调查回合，也不建设通用评论版本库。
- 不为通过验收而调整平台风控、隐藏身份或绕过登录。
- 本轮矩阵不代替之后同题 API 对照，也不将未能匿名访问解释成平台没有该内容。

## 方案比较

1. 只按代码声明能力：最快，但不能证明真实返回结构和保存回查。
2. 直接对 12 个平台大规模实时爬取：覆盖看似全面，但会混淆登录状态、页面波动和来源能力，也增加不必要请求。
3. **分层基线（本轮采用）**：先读实现与已有样本，再做少量匿名公开探测和隔离存储回查；每个结论附证据类别。它能推进 12 平台比较，同时将动态访问限制与实现缺口区分开。

## 约束与验收

- 每个平台至少有一行能力记录，且每个能力状态有文件路径、历史记录或本轮运行产物作依据；没有依据就标为未知。
- 实时请求仅使用公开搜索／公开内容入口，控制在每个平台一个查询、有限结果；遇到验证码、登录或限制即停止该平台。
- 隔离验证覆盖正文、评论及回复（若适配器实际返回）、出处和关联字段的保存与回读；不能声称完整分页，除非样本能证明页边界与下一页行为。
- 结果写入 `docs/platform-deep-collection-matrix.md`，记录验收日期与限制，供后续实现和 API 内容对照复用。

## 留给实现者的判断

如果某平台当前没有详情或讨论适配器，矩阵如实记为缺失，并按其现有搜索与公开访问方式给出最小下一步；本轮不为凑齐 12 项而实现平台功能。
