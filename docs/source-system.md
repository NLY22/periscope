# 信息源体系

Periscope 的扩源目标，是让通用搜索之外的原始资料进入同一次研究，并保留可追溯出处。来源目录、采集结果和与 API 的查询对照分开记录。

当前采集流程、评论入库、正文回填和浏览器资源控制见[采集链路与边界（2026-10-24）](collection-pipeline.md)。这轮修正保证已取得资料的保存与分层，不代表首批平台的完整深采或新版 Web 调查已全部打通。

## 当前阶段目标与框架讨论（2026-10-19）

本阶段只推进纯文本信息源获取，以 DeepSeek 等通用 Web Search API 为对照，取得其无法直接访问、难以完整获取或容易漏检的有效资料。以下是已确认的目标范围，不代表已经实现或已证实 API 无法检索。

| 主攻方向 | 目标资料 |
|---|---|
| 平台站内文字与深层讨论 | 小红书、知乎、微博等平台的文字正文、评论、楼中楼与后续补充；具体平台逐一验证接入能力 |
| 交互查询系统 | 院校、机构等按年份、专业、地区等条件查询后返回的记录，包括没有独立网页地址的数据 |
| 用户授权访问的文字内容 | 用户已有授权会话可见的帖子、讨论区与知识库内容 |

公告、文本 PDF、Word/Excel 附件、深层历史页面和公开专业数据库作为补充来源。暂不开展 OCR、音视频理解等多模态建设，也不扩展报告生成；已有能力保留。

验收以具体内容为单位：同一个问题，对 API 做合理的多问法查询，与直采取得的正文、评论、字段和记录对照，检查相关性、出处及重复获取能力。同一链接下新增的有效内容也应计入；来源配置数量和本轮 URL 差集不等于 API 的永久盲区。用户授权内容的直接访问差异，与公开资料的检索漏召回分开记录。

现有基础是来源注册、HTTP/浏览器调度、网页与文本 PDF 提取、运行记录和显式入库。完整评论树、通用多步骤交互查询、统一授权会话管理尚未形成完整通路。

框架通过逐轮问答确定，并将确认的决定持续补充在本节。

| 已确认决策 | 第一阶段约定 |
|---|---|
| 信息源范围 | 先做上述文本扩源，沿现有采集基础推进 |
| 核心问题与价值 | 用户的核心痛点是与 AI 交互时信息经常不全；系统应通过扩展来源、取得更深内容和针对性补查，逐轮缩小信息缺口，并展示已取得与尚缺资料。检索已有资料后生成回答只是其中一环，新增有效资料及其对回答的帮助才是主要价值 |
| 采集触发方式 | 按需采集为主：用户发起查询时采集，结果保存供后续复用；第一阶段不设定期采集任务 |
| 产品形态与使用者 | 最终提供重视前端体验的个人应用，网页形式可接受；当前仅供用户自己使用，同时保留 MCP 调用入口 |
| 核心交互 | 多轮调查会话：系统可以向用户询问关键条件，用户可以补充问题、调整范围，后续采集在同一调查上下文中继续深入 |
| 多轮调查主流程 | 调查会话保存上下文；用户的调查指令形成一轮，必要澄清接续原轮；在本轮预算内采集并展示资料，结束后给出带出处的简答，再等待用户继续；新指令停止旧轮并保留已采资料 |
| 指令澄清时机 | 只在关键歧义会明显改变调查方向时先询问必要问题；能开始的宽泛指令先执行，不强制用户预先给全学校、平台等条件 |
| 调查推进权 | 用户逐轮指定：每次由用户明确提出查什么，系统完成本轮任务后等待下一条指令；不自行启动下一轮或扩大调查主题，缺少关键条件时可以澄清 |
| 本轮内部调整 | 允许系统依据中间发现，在原主题、用户来源限制和本轮时间预算内改写查询词、调整采集动作、补查相关正文或评论；该权限不包含自行发起下一轮 |
| 采集中收到新指令 | 新指令优先：停止当前轮，保存已经取得的资料，再按新指令开启下一轮；不默认排队等待当前轮完成 |
| 每轮来源选择 | 系统在本轮任务范围内匹配来源；用户可以限定只查某些平台或网站，不要求每轮先手动选源或确认来源清单 |
| 每轮结果内容 | 根据本轮资料给出简短说明，附可展开的原始正文、评论、数据记录与出处；保留原始资料，不以整理回答替代原文 |
| 每轮采集预算 | 默认给采集 1–3 分钟，可手动调整；该预算不包含后续回答整理耗时，具体默认秒数在架构方案中确定 |
| 单轮过程展示 | 采集期间显示进度和陆续取得的资料，用户可以先查看；本轮采集结束后再生成基于资料的简短说明 |
| 第一版运行位置 | 先在用户本机运行采集后端、浏览器会话与资料库，通过本地网页界面和本地 MCP 使用；个人服务器部署不作为第一版前提 |
| 后端组织方式 | 第一版采用统一的本地后端，网页和 MCP 共用一套服务；内部按调查、采集和资料管理划分模块，降低启动与维护成本；不要求所有采集动作都在同一进程执行 |
| 来源能力与平台适配 | 来源能力目录逐平台声明搜索、正文、评论、回复及更新的实际支持程度与登录要求；平台适配模块处理请求、页面、分页和授权会话，统一输出资料 |
| 统一采集调度 | 调度模块选择来源、分配时间、展示进度、停止任务，并及时保存已经取得的资料；各平台适配模块不各自决定调查范围 |
| 原始资料组织 | 共享资料库分别保存帖子、评论与回复，保留平台原始编号、出处、发布时间、采集时间，以及所属帖子和回复对象关系；记录实际分页与覆盖范围，支持后续准确指向资料继续采集 |
| 资料版本与调查引用 | 各调查引用共享资料，并记录每轮实际使用的资料版本；资料更新时保留历史版本，使以前的回答仍可追溯 |
| 来源与网络异常 | 单个平台失败或需要登录时标明原因，继续其他来源并允许跳过登录；网络波动和限流只在本轮预算内有限重试 |
| 中断与整理失败 | 超时或被新指令停止时保存已采资料并标明未完成范围；模型整理失败时仍可查看原文，并可单独重试整理 |
| 第一阶段验收方式 | 12 个平台按原生讨论结构逐项实测搜索、正文、评论分页、回复关系及补新；同时验证跨轮追查、历史复用、版本引用与中断保留，并以同题、多问法 API 对照核对新增有效内容；缺失或受阻能力明确列为待完成项 |
| 首批建设重点 | 优先打通平台文字正文、评论、楼中楼和后续回复，复用已有平台适配基础，完成采集、保存和多轮追查；交互查询与授权知识库仍保留在扩源范围内 |
| 平台覆盖要求 | 用户要求覆盖足够多的平台并把能力做完整；以已有多平台适配和历史实测为基线，按平台核对搜索、正文、评论、楼中楼与后续更新，不将只完成单个平台作为首批整体验收 |
| 首批深采验收平台 | 小红书、知乎、微博、B站、抖音、快手、V2EX、GitHub、Stack Overflow、HN、CSDN、掘金，共 12 个平台，逐平台验证正文、评论及回复能力；现有学术、订阅等其他来源继续保留 |
| 平台会话接入 | 本地独立采集浏览器由用户亲自登录为首选，同时支持手动导入 Cookie 或会话文件；登录状态在本机保存复用，日常采集默认后台执行，不要求每轮打开登录窗口。首次登录、会话失效或平台要求人工确认时再提示用户处理；完整流程仍需整合 |
| 使用体验优先级 | 用户最担心操作维护麻烦；将低维护作为明确目标，尽量复用已有配置与授权会话，减少重复登录、反复配置、额外弹窗及手动文件操作；实际需要人工处理时给出清楚的操作入口 |
| 首次使用流程 | 轻量开始、按需补充：复用已有配置，只补必要模型设置；先使用可用来源，确实需要某个平台登录时再提示，允许跳过并显示未采原因 |
| 通用搜索 API 的定位 | 同时作为对照竞品和优化工具：重点建设其覆盖不足的资料获取能力，并可借用 API 做得更好的部分改善整体调查效果；不预设完全排除 API，也不预设每轮都调用 |
| 通用搜索 API 的调用策略 | 用户已配置时，由系统根据本轮问题按需调用，用于发现入口、补充公开资料或交叉核对，与平台直采配合；用户可以关闭，不要求每轮调用 |
| 历史资料复用 | 优先展示已有资料，再检查变化、补充新增评论或回复，明确标注采集时间；允许用户手动要求重新采集 |
| 大量评论的默认策略 | 在本轮预算内优先取得与当前问题相关的评论和回复，保留必要上下文并说明实际覆盖范围；不将相关片段或部分分页宣称为全量讨论 |
| 多调查的组织方式 | 不同主题使用独立调查会话，聊天与已确认条件分别保存；共享本地原始资料库，已采原文可跨调查复用 |
| 对话与整理模型 | 第一版先使用外部模型 API，由用户配置自己的密钥和模型提供商，优先复用已有模型接入能力；该选择与通用搜索 API 的角色分开 |
| 设计讨论方式 | 实现前继续逐轮问答，确认目标细节并持续记录；已提出的框架建议不视为用户已确认的实现方案 |

已确定第一版以统一的本地后端承接个人界面与 MCP，复用同一套调查、采集和资料管理能力；这是目标组织方式，不代表现有 Web/MCP 已完整接通新版采集。当前继续聚焦扩源，不提前建设多人产品。

多轮交互用于推进资料调查与采集，不将本阶段扩大为报告生成功能建设。旧研究链已有会话、追问与范围调整机制，新版采集主干仍是单轮查询；后续评估复用这些机制，尚未完成统一。

目标、主流程、模块分工、异常处理及验收方向已确认，汇总见[本地多轮调查与信息源框架设计](superpowers/specs/2026-10-19-local-investigation-source-framework-design.md)。该设计中的工程细节供用户审阅，尚未实施。逐平台深采能力仍需以实际样本验证，已有搜索入口或搜索卡片不代表详情和评论已可稳定采集。视频平台先处理文字描述、评论及回复，多模态仍不纳入本阶段。

除下列固定来源外，现可通过 `--crawl` 自动跟进本轮链接，或使用 `--crawl-seeds` 从站点入口自主发现详情、站点地图与 PDF 附件，提取后接入检索和语料保存。详见[自主爬虫](native-crawler.md)。

## 当前范围

截至本次重构，共登记 **184 个来源配置**。默认话题查询的 HTTP 计划包含 **25 个搜索入口和 84 个订阅源**；它们按时间预算执行，登记或进入计划均不代表在线可用。

| 检索方式 | 已登记配置 | 实际行为与限制 |
|---|---:|---|
| 搜索 | 27 | 默认使用 25 个入口；另两个是重复或时间窗口配方，可显式选择 |
| 订阅源 | 84 | 查询当前窗口，并按话题过滤；不代表完整历史 |
| 页面 | 20 | 显式选中后提取链接、过滤相关条目；不是站内全文搜索 |
| 浏览器 | 13 | 深度模式调用已有的小红书、抖音、快手适配；其余保持跳过并说明原因 |
| 固定快照 | 40 | 保留目录与已有批量采集能力，不作为任意话题搜索入口 |

原有平台搜索、arXiv、OpenAlex、GitHub 仓库、HN、npm、Google News，以及官方、媒体、政策等订阅源进入统一调度。本次增加五个搜索入口：

| 入口 | 能补充的材料 |
|---|---|
| GitHub Issues / PR | 实际问题、改动讨论、原帖正文与评论数 |
| Stack Overflow | 技术问答的题干、时间、评分、回答数与浏览数 |
| Hugging Face 模型 | 模型身份、原始链接、下载和点赞指标 |
| Hugging Face 数据集 | 数据集身份、原始链接、下载和点赞指标 |
| Crossref | 论文标题、DOI、作者字段及可用摘要等出版元数据 |

这些是一手平台接口，与通用网页搜索协同。Crossref 记录不等于论文全文，模型或数据集条目也不等于已阅读其完整说明。已有 HTTP 解析器通常最多保留 1,200 字符文本；视频字幕和评论仍通过可选富化处理。

## 使用

```text
periscope-topic --list-sources
periscope-topic --topic "人形机器人"
periscope-topic --topic "retrieval augmented generation" --source-kinds academic --no-api
periscope-topic --topic "DeepSeek" --sources github_issues hf_model_search crossref_works --no-api
periscope-topic --topic "人形机器人" --budget 60 --json results.json
periscope-topic --topic "人形机器人" --coverage focused
```

`--sources`、`--source-kinds` 筛选直采部分；历史语料和搜索 API 可分别用 `--no-local`、`--no-api` 关闭。`--cached-only` 只读历史语料。`--coverage focused` 恢复原有平台查询范围；直接调用库的 `TopicRequest` 仍默认 focused，以兼容原有调用方，使用 `coverage="broad"` 开启广泛来源。

`--budget` 限制直采总时间，不包含 API 查询、本地检索和可选富化；0 表示没有总时限，单源仍有超时保护。请求限制并发、同主机串行并遵守间隔。深度模式共享浏览器与 HTTP 总预算。已完成的页在后续超时时保留，状态标为部分成功。

## 自定义来源

使用 `--sources-file sources.json` 追加研究所、院校、政府、行业组织等公开 RSS/Atom 或已有明确结构的接口。配置与系统目录共同调度，不需要改动编排代码。

```json
{
  "sources": [
    {
      "key": "institution_updates",
      "name": "机构公开更新（替换成真实订阅地址）",
      "url": "https://example.org/feed.xml",
      "kind": "official",
      "fmt": "rss",
      "max_pages": 1
    }
  ],
  "disabled_sources": ["youtube_cn"]
}
```

示例地址是占位。搜索接口在 `url` 中使用 `{query}`，JSON 接口使用 `items_path`、`title`、`url_field`、`date_field`、`author_field`、`text_field` 声明字段路径。配置格式采用 `periscope.collection.models.Source`，元组字段用 JSON 数组表示。重复键、未知来源、无效参数和不能入库的类别会提前报错。来源列表只展示配置说明，不输出请求头、Cookie 或凭据。

## 结果、出处与 API 对照

JSON 和运行记录保留逐源 `source_reports`，包括尝试状态、请求数、条数、过滤与无链接条数、耗时和错误。主要状态为成功、空结果、失败、部分成功、单源超时、未赶上总预算、跳过。返回登录页、损坏订阅或错误 JSON 结构会记录为失败。

每条直采资料包含源键、类别、采集方式、观察时间及原始链接。原生资料按规范链接识别，不会仅因为标题都叫“DeepSeek”就合并论文、Issues 和评论。同一链接从 API 与直采返回也不会被算作两家独立支撑。展示聚合保留成员列表；借用另一条结果的较长正文时，同时保留 `body_source_url`。这些字段贯穿分片、显式入库与历史回读。

API 请求成功时，`coverage.direct_urls_not_in_api` 表示**本轮 API 返回集合中没有的直采链接数**。关闭 API、缺少凭据或请求失败时，该值为 `null`，不会冒充“独家来源”。它不证明 API 永远无法检索该内容，也不直接代表相关性或报告质量提升。
